Versões, tags e publicação

release.json é a fonte da versão do jogo. Godot 4.7.2 stable .NET, schema de save e protocolo de rede têm versões independentes. Incrementar o jogo não migra saves nem torna clientes incompatíveis automaticamente.

O marco v0.1.0-alpha já foi publicado. Não repetir o bootstrap neste repositório. As próximas integrações seguem a automação descrita abaixo.

Uma integração, uma versão

Integrar PRs por squash merge, com título Conventional Commits:

Título Incremento
feat: ... MINOR; PATCH volta a zero
fix: ..., refactor: ..., perf: ..., revert: ... PATCH
feat!: ... ou rodapé BREAKING CHANGE: motivo MAJOR; MINOR/PATCH voltam a zero
docs, test, ci, build, chore, style Sem versão do jogo

Esta é uma convenção do projeto baseada em SemVer e Conventional Commits. Se uma mudança técnica altera o comportamento distribuído, classificá-la como feature, fix/refatoração ou quebra, em vez de escondê-la em chore/build. O check de título também recusa tipos desconhecidos; não infere impacto pelo diff.

Exemplo: 0.1.0-alpha → fix 0.1.1-alpha → feature 0.2.0-alpha → quebra 1.0.0-alpha. 1.0.0-alpha continua experimental. A promoção para beta/estável é uma decisão explícita; a automação não remove -alpha.

Prévia e sincronização

python -B Tools/release_version.py preview
python -B Tools/release_version.py apply
python -B Tools/release_version.py check
python -B Tools/release_version.py title --title "feat: nova interação"
python -m unittest discover -s Tests -p "test_release*.py"

A sincronização atualiza configuração Godot, metadados .NET, marcadores do README/HTML de entrada e a página de versão. Números em documentos históricos permanecem como evidência de sua época. As telas leem ProjectSettings.

Marco inicial e ativação

O workflow Release and documentation fica disponível depois que os novos arquivos estiverem consolidados na main. Não cria tag sobre o HEAD antigo enquanto houver trabalho local ainda não integrado.

  1. Revisar os arquivos locais e consolidar somente o conteúdo pretendido.
  2. Validar Python, CoreTests, C#, importação e versão renderizada no Godot.
  3. Confirmar Actions com contents:write, squash merge, proteção da main compatível com o bot e Pages no repositório público com origem GitHub Actions. Não remover proteções para contornar rejeições; usar exceção restrita ao publicador, se necessária. O preparo pode ser repetido com python -B Tools/github_release_setup.py --apply: configura squash por título/descrição do PR e tenta habilitar Pages, sem mudar visibilidade, cobrança, proteções ou permissões globais do token.
  4. Executar o workflow manual com bootstrap=true. Ele valida e publica v0.1.0-alpha, anotada, no estado consolidado. Não reconstrói tags antigas.
  5. Nas próximas integrações, a publicação ocorre automaticamente.

O portal é publicado no repositório público separado Operation-Spencer-Docs, enquanto o código do jogo e suas releases permanecem privados. O endereço é https://felipestroff.github.io/Operation-Spencer-Docs/. A configuração inicial de 15/10 encontrou restrição de Pages no repositório privado; a hospedagem separada substitui esse destino, sem alterar visibilidade ou cobrança.

O fluxo automático usa PAGES_ENABLED=true e o secret DOCS_PUBLISH_KEY, uma chave SSH com escrita exclusiva no repositório de documentação. O job privado valida e envia somente o site estático; o workflow público publica o Pages. O preparo python -B Tools/github_release_setup.py --apply passa a configurar Pages no destino público existente. Ver publicação da documentação.

Concorrência, falhas e recuperação

O workflow percorre os commits de primeira linha desde o cursor automation.last_processed_sha. Mesmo se o GitHub substituir uma execução pendente, o próximo processamento recupera todas as integrações ainda não tratadas.

Cada versão recebe um commit de metadados cujo pai é o SHA da integração original; código e assets são exatamente os daquele ponto. Um checkpoint separado atualiza a main. Isso permite várias integrações pendentes sem incluir código posterior em uma tag anterior. O changelog contém links aos commits e os títulos squash mantêm o número do PR quando fornecido pelo GitHub.

O envio da main e de todas as tags é atômico, sem force push. Se a branch avançar, a publicação recusa o plano antigo: executar novamente sobre a nova main. Nenhuma tag existente é movida. As validações ocorrem antes do envio.

As anotações das tags funcionam como registro durável das notas. Se a API falhar depois do push, a próxima execução recria apenas as GitHub Releases ausentes. O workflow chama Pages explicitamente, pois eventos criados com GITHUB_TOKEN normalmente não iniciam outro workflow. Releases são prereleases de fontes; não incluem executáveis nem certificam uma partida multiplayer.

Para diagnóstico sem publicar:

python -B Tools/publish_release.py prepare --bootstrap
# Sem --bootstrap depois do marco. Plano em Build/release-plan.json.

prepare exige checkout limpo e escreve apenas objetos Git/worktrees temporárias e o plano ignorado. push e repair são operações de publicação do CI.

Se o preparo informar Checkout sujo, a mensagem lista os arquivos afetados. Inspecionar o status e o diff antes de repetir; não limpar ou consolidar arquivos automaticamente para contornar a proteção. Os arquivos *.import usam LF explícito em .gitattributes: o Godot os regrava com LF, e um checkout Windows com core.autocrlf=true pode marcá-los como modificados após a importação mesmo quando não há diferença de conteúdo. O teste de regressão reproduz esse caso em clones Git temporários, verifica a política LF e mantém a detecção de mudanças reais. Em um runner novo, a regra é aplicada já no checkout.
